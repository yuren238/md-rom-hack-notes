# 04 · 水印与模式指示器的定位与移除

> 本节的"水印"指译文组在画面中添加的署名标识（记为 **WM**，共 2 处变体）；"模式指示器"指战斗中常驻显示的四个难度档位名称（记为 **MODE0–MODE3**）。
> 所有操作在 `BASE-UNP`（保护已移除）上进行，避免被反修改机制反制。

## 4.1 水印定位链

### 第一步：排除"字体绘制"假设

最初根据截图判断水印是**用中文点阵字库当文字绘制**的，理由是截图中出现的持续时间与位置变化（顶部 / 右下角随场景变化）像是绘制调用行为。据此计划去 NOP 绘制调用。

**该判断后来被否定**：把 `0xDF86E` 按 1bpp / 2bpp / 4bpp × 24 种 tile 排列穷举渲染，都不呈现字形特征——它是 4bpp 图形集，不是字库。

### 第二步：在资源清单里找形状

把全部 31 个容器资源按解码尺寸排序，发现**两个相邻的 384 字节（12 tiles）块**：

| 资源地址 | 规格 | 内容 |
|---|---|---|
| `0x0DFD02` | 12 tiles | 署名水印（变体 B，列优先排列） |
| `0x0DFE54` | 12 tiles | 署名水印（变体 A，行优先排列） |

两者解码后**形状完全相同、调色板索引不同**：

```
变体 A 非零 nibble 分布: 5,5,B,B
变体 B 非零 nibble 分布: A,A,4,4,3,3
两者非零字节数均为 267
```

**它们都是同一份署名水印**，只是供不同画面使用不同的调色板变体。

### 第三步：确认无第三份拷贝

以"非零 nibble 的 64 bit 形状掩码"为准，在**原始 ROM + 全部已解码的容器资源**中做全量搜索，结果：**只有这两个 blob 含水印形状**，不存在第三份。

### 第四步：找引用

全 ROM 搜索资源地址（32 位大端），**唯一引用点 = `0x45A26` / `0x45A2A`**，位于资源装载表内。

## 4.2 资源装载系统（完整逆向）

### 装载表 `0x45A0A`

结构：`{word: VRAM tile 基址, long: 资源地址}`，以 `0xFFFF` 结尾。

| tile 基址 | 资源地址 | 内容 | 占用 tiles |
|---|---|---|---|
| 0x00C8 | 0x16C148 | 图形 | — |
| 0x00D1 | 0x16C080 | 图形 | — |
| 0x00DC | 0x16C1F4 | 图形 | — |
| 0x0680 | 0x0DF86E | 特殊字形集 | 0x680–0x6ED |
| 0x07C0 | 0x0E7652 | ASCII 字库 | 0x7C0–0x7FF |
| **0x06B4** | **0x0DFE54** | **水印 变体 A** | **0x6B4–0x6BF** |
| **0x06EE** | **0x0DFD02** | **水印 变体 B** | **0x6EE–0x6F9** |

### 装载器 `0x454F2`

位于开机初始化段，**全 ROM 仅此一处引用该表**：

```
0454F2  lea   $45A0A,a1          ; 表首址
0454F8  move.w (a1)+,d0          ; tile 基址参数
0454FA  bmi   $4550E             ; 0xFFFF = 表尾
0454FC  move.l (a1)+,d1 -> a0    ; 资源地址
045500  jsr   $44BFA             ; 设置 VRAM 写入目标
045506  jsr   $445A6             ; 解码 → 写 VRAM（长度由 0x00 终止符决定）
04550C  bra   $454F8
```

### 水印的显示方式

**没有动态绘制代码**。水印 tile 由**各场景的 tilemap 数据直接引用**：

- 地图字 `0x26B4`–`0x26BF`（palette 1 + tile 0x6B4–0x6BF）共 197 处
- 地图字 `0x26EE`–`0x26F9`（palette 1 + tile 0x6EE–0x6F9）共 257 处
- 另有代码后数据表 `0x45A36` 起（`20C9×6 + 26B4..26B9` 等）

**这就是第一版补丁失败的原因**：不同场景引用不同变体，只处理一个 blob，另一半场景的水印自然还在。

## 4.3 移除补丁

**思路**：不去改 14 处以上的地图数据，而是让**水印贴图本身变全透明**——所有场景一次性生效。

### 字节操作

把 blob 魔数之后的控制流替换为"解码出 384 个 `0x00`"的最小流：

```
0xDFE58: 01 00 89 07 70 00  ->  01 00 FF FF FE 00     （仅 3 字节不同）
```

新流解读：`1` 个字面量(`00`) + RLE×128 + RLE×128 + RLE×127 = **384 个 `0x00`** = 12 个全透明 tile，末字节 `0x00` 终止。

> ⚠️ **RLE 控制字节必须 ≥ 0x80**：重复 127 次是 `0xFE`，写成 `0x7E` 会被当成"126 个字面量"，解码长度立刻出错——第一次试补就是栽在这个细节上。

### 结果

| 项 | 值 |
|---|---|
| 改动位置 | 2 个水印 blob 的流头部 |
| 改动字节数 | 6 |
| 地图数据 | 未改动 |
| 代码 / 指针 / 校验和 | 未触及 |

## 4.4 模式指示器的定位与移除

### 为什么它不是"水印"而是功能 UI

它显示的是**当前选中的难度档位名称**（MODE0–MODE3 四选一），随游戏开始时选择的模式变化，属于译文组新增的难度系统的一部分。

### 定位方法：从变量反查代码

已知模式值存放于 RAM `$FF5FA3`。**搜索该地址的全 ROM 引用**（`00 FF 5F A3`），共 41 处，其中 7 处落在译文组新增代码区 `0xDB604–0xDE124` 内。逐个反汇编后命中：

```
0DC65E  movem.l d0-d1/a0-a1,-(a7)
0DC662  lea     $DC6E2(pc),a1        ; ← 资源表
0DC666  move.w  (a1)+,d0             ; 元素 1 的 VRAM 基址
0DC668  movea.l (a1)+,a0             ; 元素 1 资源
0DC66A  cmpi.b  #$2,$FF5FA0.l        ; 语言/版本标志？
0DC674  movea.l (a1),a0              ; 是则取备用资源
...
0DC694  moveq   #0,d0
0DC696  move.b  $FF5FA3.l,d1         ; d1 = 模式值 0..3
0DC69C  lsl.w   #$2,d1               ; ×4（long 表项）
0DC69E  move.w  (a1)+,d0             ; 模式名的 VRAM 基址
0DC6A0  cmpi.b  #$2,$FF5FA0.l
0DC6AA  addi.w  #$10,d1              ; 标志=2 时改用英文组
0DC6AE  movea.l (a1,d1.w),a0         ; ← 按模式索引资源
0DC6B2  jsr     $44BFA               ; 设置 VRAM 目标
0DC6B8  jsr     $445A6               ; 解码 → 写 VRAM
```

**这与水印装载器 `0x454F2` 是同一套调用模式**（`jsr $44BFA` 设目标 + `jsr $445A6` 解码）。

### 资源表 `0xDC6E2`

| 表项 | VRAM | 资源 | 内容 |
|---|---|---|---|
| res1 | 0x6E0 | `0x374C3E` / 备用 `0x374CF4` | `MODE` 标签（中 / 英各一份） |
| res2 | 0x6D8 | `0x3749E0` | 配套元素 8 tiles |
| 模式名 | 0x6FA | `d1 = $FF5FA3 × 4` 索引 | MODE0 `0x0F7DB0` / MODE1 `0x0F7E64` / MODE2 `0x0F7F12` / MODE3 `0x374D7A` |
| 英文组 | 同上 +0x10 | `$FF5FA0 == 2` 时 | `EASY`/`NORMAL`/`HARD`/`HIDDEN` |

（`0x374E26` / `0x374EAA` / `0x374F6E` / `0x374FF4`）

### 引用唯一性检查

对 11 个资源的 32 位地址做全 ROM 搜索：**每个地址各只出现 1 次**（即本表内），无任何其他画面共用 → 全部清零零风险。

> 注意：开始菜单里的难度选择界面**不是**用这些 blob 绘制的（它走字体绘制），因此移除指示器不会影响菜单，难度仍可正常选择。

### 补丁

每个 blob 的流替换为"解码出等长全零"的最小流：

| 解码长度 | 替换流 | 说明 |
|---|---|---|
| 192 B（6 tiles） | `01 00 FF BE 00` | 1 + 128 + 63 |
| 256 B（8 tiles） | `01 00 FF FE 00` | 1 + 128 + 127 |

## 4.5 最终补丁汇总

一次完成 **2 个水印 blob + 11 个模式指示器 blob = 13 处，共 50 字节**：

| # | 地址 | 内容 | 解码长度 |
|---|---|---|---|
| 1 | `0x0DFE54` | 水印 变体 A | 384 B |
| 2 | `0x0DFD02` | 水印 变体 B | 384 B |
| 3 | `0x374C3E` | `MODE` 标签（中） | 192 B |
| 4 | `0x374CF4` | `MODE` 标签（英） | 192 B |
| 5 | `0x3749E0` | 配套元素 res2 | 256 B |
| 6–9 | `0x0F7DB0` / `0x0F7E64` / `0x0F7F12` / `0x374D7A` | MODE0–MODE3 | 192 B |
| 10–13 | `0x374E26` / `0x374EAA` / `0x374F6E` / `0x374FF4` | `EASY`/`NORMAL`/`HARD`/`HIDDEN` | 192 B |

工具 `tools/patch_tool.py` 内含**逐 blob 解码验证**：补丁后重新解码每个 blob，确认长度一致且全为零，任一不符即中止且不写出文件。

## 4.6 安全性分析

| 检查项 | 结论 |
|---|---|
| 引用唯一性 | ✅ 13 个 blob 仅被各自的装载表引用一次（全 ROM 地址搜索确认） |
| 是否影响其他画面 | ✅ 无其他画面共用这些 tiles；若某场景另行上传图形到这些 tile，会正常覆盖 |
| 是否破坏可见内容 | ✅ 被透明化的 tile 当前显示的正是水印/指示器像素本身 |
| 是否触及代码 | ✅ 否。改动全部位于图形数据流内部 |
| 是否触及校验和 | ✅ 否（基底已无校验）。若换用未去保护的基底，则必须重算头部校验和 |
| 地图数据 | ✅ 未改动（这正是选择"透明化贴图"而非"清理 14+ 处地图引用"的原因） |

## 4.7 回归测试清单

1. 新开档 → 序章对话文本正常（验证字库未被破坏）
2. 野外场景 → 顶部水印消失、画面其余部分正常
3. 进入战斗 → 右下角水印与左下角模式指示器均消失、无花屏
4. 战斗胜利 / 逃跑 / 全灭 → 正常返回
5. 开始菜单 → 四个难度档位仍可正常显示与选择
6. 存档 / 读档正常

## 4.8 遗留说明

- 水印与指示器全部移除后，ROM 中已无可见的译文组署名标识（头部版权串未改动）。
- 装载器的 VDP 写入时序问题（CPU 直写 VRAM、无 VBlank 同步）与水印无关，未修复。在精确模拟 VDP 写时序的模拟器上仍可能出现文字/图形异常，建议使用兼容性更宽松的模拟器测试。
