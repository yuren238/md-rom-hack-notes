# 01 · ROM 头部与差异区块分析

> 分析对象：`BASE-CN`（4,194,304 B / 32 Mbit），对照物：`BASE-JP`（日文原版，3,145,728 B / 24 Mbit）与 `BASE-EU`（欧洲版，同尺寸 24 Mbit）。

## 1.1 头部字段对比

| 字段 | 偏移 | BASE-CN | BASE-EU | 说明 |
|---|---|---|---|---|
| 版权串 | 0x110 | `(C)<GROUP> 2026.FEB` | `(C)<PUBLISHER> 1995.AUG` | 译文组改写 |
| 国内名 | 0x120 | GBK 中文标题 + 版本号 + 译者署名 | 英文原名 | 译文组改写 |
| 国际名 | 0x150 | 原英文名后追加 `-Rebuilt` | 英文原名 | — |
| 序列号 | 0x180 | `GM <内码> -00` | `GM <料号> -1307` | 与日版料号一致，区域不同 |
| 区域码 | 0x1F0 | `J` | `8` | 区域不同 |
| ROM 范围 | 0x1A0 | `0x000000–0x3FFFFF` | `0x000000–0x2FFFFF` | 译文版扩容 1 MB |
| SRAM 范围 | 0x1B8 | `0x0020FFFF`（64 KB） | `0x00203FFF`（16 KB） | 译文版把 SRAM 扩到 4 倍 |
| 头部校验和 | 0x18E | 实测值 0x4B54 / 重算 0x40C8 **不符** | 实测 0x7FC0 / 重算 0xF3A6 **不符** | 两份都未修复校验和 |
| 复位向量 PC | 0x004 | `0x00000200` | `0x00000220` | 入口不同 |
| 中断向量表 | 0x000–0x0FF | 未用向量统一指向 `0x0000055A` | 统一指向 `0x00000200` | 译文版自定义入口 |

## 1.2 基底判定

结论：**`BASE-CN` 的基底是日文原版的 32 Mbit 扩容版**，不是欧洲版。

判据：

1. 译文版序列号（0x180）与日版料号一致，与欧洲版不同；
2. 前 3 MB 内与欧洲版有 **94.40%** 的字节不一致（46,618 个差异段）——远超正常区域差异；
3. 复位向量与整个中断向量表都不同。

**所以：拿欧洲版做"原版覆盖"会产生完全无法运行的镜像。** 需要日文原版才能做字节级还原。

## 1.3 差异区块概览

| 偏移范围 | 长度 | 类型 | 依据 |
|---|---|---|---|
| 0x000100–0x000200 | 0x100 | 头部 | 版权/名称/序列号/区域/校验和全部被改 |
| 0x000000–0x000008 | 8 | 中断向量 | 全部改为自定义入口 |
| 0x000200–0x00300000 | ~3 MB | 混合 | 94.4% 不同（区域差异 + **资源重新编码**） |
| 0x00300000–0x00400000 | 1 MB | 扩容新增区 | 以 `MAGIC2` 开头，熵 5.65–6.5，密集资源块 |
| 0x00258000–0x00350000 | ~1 MB | 容器块序列 | `MAGIC2` 以 0x2000/0x906/0x566 等固定间隔重复出现 254 次 |

差异率高达 94% 的**根本原因**：译文组用自己的压缩容器重新编码了绝大部分图形资源，即使画面内容与原版相同，字节也几乎全部不同。这排除了"按内容比对"的捷径——必须先逆出容器格式。

## 1.4 指令级对齐：为什么不能做字节级覆盖

把日文原版与译文版的引导段做指令级对照，结果：

```
原版 0x16628:  660A  4254  33FC 0016 FFFF 4100  4E75
译文版 0x19124: 660A  4254  33FC 0016 FFFF 4100  4E75
```

**逐指令完全一致**，但整体位移 `+0x2AFC`，且所有绝对地址被改写、中间插入了新指令。这是"反汇编 → 加料 → 重汇编"的典型特征，不是二进制补丁。

**推论**：译文版与任何原版之间不存在"改回几个字节就还原"的关系。任何移除动作都只能是"把新增的调用/资源失效化"，而不是还原。

## 1.5 校验和修复（通用）

译文版与欧洲版的头部校验和**都不正确**。修改 ROM 后若需让严格校验的模拟器/烧录卡接受，需重算 0x200 起的 16 位和并写回 0x18E：

```python
data = bytearray(open(rom_path, 'rb').read())
s = 0
for i in range(0x200, len(data), 2):
    s = (s + ((data[i] << 8) | data[i + 1])) & 0xFFFF
data[0x18E] = s >> 8
data[0x18F] = s & 0xFF
```

> 注：本项目的补丁目标 ROM 已被第三方**主动放弃**头部校验（其配套版本说明明确写着移除了校验机制），因此补丁后无需重算。但换成未去保护的基底时，这一步是必须的。

## 1.6 一个重要的反面教训

在分析初期，曾经得出过这样的结论：

> "ROM 内校验是模拟器无关的——既然宽松模拟器能正常运行，就不存在 ROM 内的保护机制。"

**这个结论是错的**，因为它的隐含前提是"保护 = 启动时检查"。
实际保护是**被修改后才武装**的（详见 [`03-protection-system.md`](03-protection-system.md)），未改动的 ROM 永远不会触发它。

教训：**"在未修改状态下运行正常"不能作为"不存在保护"的证据。** 判断保护是否存在，唯一可靠的方法是做一次验证性修改并观察行为变化。
