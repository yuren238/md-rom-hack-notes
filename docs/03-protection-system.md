# 03 · 反修改保护系统完整逆向

译文版内置了一套**三层反修改保护**。它的关键特征是：**未改动的 ROM 永远不会触发它**，因此单靠静态阅读汇编（甚至单靠"跑起来正常"）都判断不出它存在。

本文数据来源：`BASE-CN` 与 `BASE-UNP`（第三方在该版本基础上"彻底移除 ROM 防修改校验"的改版）逐字节 diff —— 两者同为 4 MB，差异仅 **722 字节 / 17 处（0.0172%）**。这份 diff 是定位全部保护地址的关键锚点。

## 3.1 第一层：SRAM 密钥 + 代码自解密

防止"直接改代码区"。

| 地址 | 行为 | 作用 |
|---|---|---|
| `0x46452` | 对 ROM `0xDB604–0xDE124` 做 32 位累加和 → 写入 SRAM `$203FF8`（先 `move.b #$1,$A130F1` 切换 SRAM bank） | 生成"密钥"并存进 SRAM |
| `0x551A6` | 读 SRAM `$203FF8` 作为 XOR 密钥 → 把 ROM `0x551DE` 起的代码解密复制到 RAM `$FF0000` → `jmp $FF0000` | 运行时解密执行 |

**机制**：`0xDB604–0xDE124` 这段数据一旦被改动 → 密钥改变 → `$FF0000` 处解出一堆垃圾指令 → 崩溃或花屏。

**为什么静态分析看不到**：ROM 中 `0x551DE` 处的字节**本身就是密文**，反汇编器出来的是无意义指令。必须先发现"密钥来自某段数据的累加和"这条线索，手动解密后才能阅读真正的代码。

## 3.2 第二层：周期性校验 + 间接跳转劫持（真正的"防修改校验"）

| 地址 | 行为 |
|---|---|
| `0x53A` | 中断处理程序，**每帧**调用 `jsr $D8B92` |
| `0xD8B92` | 把 `[$FF4FF4]`、`[$FF4FF8]` 累加进 `[$FFFFFFF8]`；当 `[$FF4FF4]` 等于魔数 `"0523"`（`$30353233`）时，比对 `[$FFFFFFF8]` 与 `ROM[0xDF86A] XOR ROM[0x12A]`；**不符 → 把 `$FF4FFC` 改写为 `0x451D0`** |
| `0xD8A72` | 配套的计数 / 武装例程（管理 `$FF4FF0`，写入 `"0523"` 标记） |
| `0x4515E` | **劫持点**：`movea.l $FF4FFC.l,a0` + `jmp (a0)` —— 正常情况下 `a0 = 0x45166`（正常的调色板/图形例程）；被劫持时 `a0 = 0x451D0`（**画面破坏例程**：逐 nibble 递减颜色 → 花屏） |

**为什么静态分析看不到**：

1. 触发条件是**一个埋在数据里的魔数** `"0523"`。不追到 `0xD8B92` 内部，完全不知道"什么时候才比对"。
2. 劫持点 `0x4515E` 是一个 `jmp (a0)` 形式的**合法间接跳转**——静态看毫无异常。只有知道 `$FF4FFC` 会被改写，才能理解这里是个开关。
3. 破坏效果是**画面渐变花屏**，非常容易被误判为"模拟器兼容性问题"或"VDP 时序问题"。

## 3.3 第三层：SRAM 计数 / 惩罚触发

| 地址 | 行为 |
|---|---|
| `0x3A4` | 读 SRAM `$204010`，非零则写回（存档 / 计数） |
| `0x5982` | 读 SRAM `$203FF4` 与当前值比对，不符 → `move.b #$88,$EE45`（惩罚标志） |
| `0x8D5E` | 向 SRAM `$203FF4` 写入计数值 |
| `0x45238` | SRAM bank 操作 + `lea $203FF1` |
| `0x5AE3A` | `move.w #$9E,$ECA8` + `moveq #1,d7` —— **强制遣返 / 惩罚触发** |
| `0xDB930` | SRAM `$204010` 校验（比对魔数 `"0523"` 与 `$12A` 异或） |
| `0xDC407` / `0xDC457` / `0xDE0D8` | SRAM bank 切换 + `$203FF?` 读写 |

这一层单独看每一处都只是普通的 SRAM 读写，没有任何"异常"特征——**只有和前两层串起来才看得出是保护系统**。

## 3.4 `BASE-UNP` 如何拆除保护（17 处、722 字节）

| 优化项 | 涉及地址 | 手法 |
|---|---|---|
| 移除 ROM 防修改校验 | `0x3A4`、`0x53A`、`0x5982`、`0x8D5E`、`0x45238`、`0xD8A72`、`0xD8B92`、`0xDB930`、`0xDC407`、`0xDC457`、`0xDE0D8`、`0x46452` | 全部改写为 `4E71`（NOP）填充 |
| **关键：解除劫持跳板** | `0x4515E` | `movea.l $FF4FFC.l,a0 / jmp (a0)` → 改为无条件 `jmp $45166`（永远走正常例程，不可能被劫持） |
| 替代解密执行 | `0x551A6` | 解密 + JMP 改为 `jsr $DB604` + 查表跳转（表位于 ROM `0xEF8C0`） |
| 废除即时存档回退惩罚 | `0x5AE3A` | 改为 `moveq #0,d7 / rts` |
| 新游戏可选隐藏难度 | 依赖模式变量 RAM `$FF5FA3` | 见下 |
| 经验衰减阈值改为动态 | `0x3430` | 原 `cmpi.w #$26` / `subi.w #$25` → `jsr $DB610` |

新增例程 `0xDB604`（`BASE-UNP`）：

```
0DB604  moveq #0,d0 / rts              ; 占位
0DB610  move.w $8(a0),d0               ; 取等级
        cmpi.b #$3,$FF5FA3.l           ; 模式 == 3（最高档）?
        beq  -> subi.w #$29,d0         ;   -> 衰减起点 42 级
        subi.w #$33,d0                 ; 否则 -> 衰减起点 52 级
        rts
```

**拆除效果核对**（常量引用计数，改前 → 改后）：

`$FF4FFC` 3→1、`$FF4FF0` 1→0、`$FF4FF4` 2→0、`$203FF8` 2→0、`$203FF4` 2→0、`$204010` 3→0、`$D8B92` 1→0、`$D8A72` 1→0、`$A130F1` 78→56。
唯一残留的 `$FF4FFC` 位于 `0x398`（初始化时写入正常值 `0x45166`，无害）。

## 3.5 静态分析的边界：一次真实的误判复盘

分析初期曾给出过明确结论：

> "ROM 内校验是模拟器无关的——既然宽松模拟器能正常跑，就**不存在**只在精确模拟器上触发的 ROM 内限制。"

**这是错的。** 推理的隐含前提是"保护 = 启动时检查"，而真实机制是"**保护 = 被改动后才武装**"。

### 为什么这套设计对静态分析特别不友好

| 层 | 静态分析的障碍 |
|---|---|
| 1 | ROM 中存放的是**密文**，不先解出密钥就反汇编不出任何有意义的内容 |
| 2 | 触发条件是**埋在数据里的魔数**；劫持点是一句**语法合法的间接跳转**；破坏效果是**花屏**（极易归因到模拟器/时序） |
| 3 | 每一处都只是普通的 SRAM 读写，**孤立看没有任何可疑特征** |

对比之下，同时期独立解出的部分（容器格式、资源装载表、水印定位）都有一个共同点：**有结构、有引用链、有规律**。而这套保护的设计目标恰恰是**去结构化**。这就是它难以静态发现的原因。

### 什么方法能找到它

**动态实证**是唯一可靠路径：

1. 做一次**验证性修改**（改一个字节即可）；
2. 运行并**观察行为变化**（是否花屏、是否跳字、是否崩溃）；
3. 二分定位被校验的区域；
4. 再把校验例程反汇编出来。

如果一开始就按这条路线走，很可能在早期就撞上保护；但当时选择了纯静态推理，并把已有的动态异常（精确模拟器上出现的乱码/跳字）用"时序不兼容"解释掉了——**这是方法论上的失误，不是信息不足**。

### 另一条路：全量反汇编的体力活

若不依赖 diff 锚点，理论上也可以发现：把中断处理程序里所有 `jsr` 逐个跟进（包括跟踪到 RAM 中的自解密代码段），再对全 ROM 的间接跳转目标做一次穷举反汇编。这不是做不到，只是成本高、且需要先有"可能存在保护"的假设才会去做。

> **结论**：在没有"确实存在保护"这一存在性证据的前提下，纯静态分析很难主动发现它。`BASE-UNP` 提供的是**存在性证明**与**定位锚点**（722 字节 diff），而不是答案本身。

## 3.6 对后续打补丁的意义

- `BASE-UNP` 已移除全部三层保护，且其**图形资源与 `BASE-CN` 完全一致**（逐区 MD5 相同：字形集、CG 库、UI 文字、ASCII 字库、装载器代码区均未改动）。
- 因此 `BASE-UNP` 是**打补丁的最佳基底**：改动不会被反制。
- **但装载器代码未改**：容器采用 CPU 直写 VRAM、无 VBlank 同步，在精确模拟 VDP 写时序的模拟器上仍可能显示异常。这与保护机制无关，属于译文版自身的可移植性缺陷，未在本项目中修复。
- 一个可判定二者因果的实验：把 `BASE-UNP` 放到精确模拟器上运行。若仍乱码 → 原因在装载器时序；若恢复正常 → 说明先前的乱码正是**保护惩罚例程 `0x451D0`（故意破坏画面）**被触发。
